# SAND.O reuse assessment

## Best small candidate: velocity-aware stopping distance

The most practical SAND.O idea for the current policy interface is its per-axis, acceleration-limited graph transition model in [`GraphSearch::computeNodeTime`](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/src/hgp/graph_search.cpp#L404-L547). Given start/target position, current velocity, and configured maximum acceleration and speed, it computes a transition duration and candidate terminal velocity. For motion initially aimed away from a target, it explicitly includes the distance to stop, `v0²/(2 a_max)`, before accelerating toward it.

That principle could be adapted as an **offline speed-limit diagnostic** for learned velocity commands near waypoints or the window: estimate distance remaining along the target direction and limit commanded speed using measured deceleration, e.g. `v_cap = sqrt(2 * a_brake * d_remaining)`. It could reveal whether a trajectory asks PX4 to stop inside an infeasible distance and help shape a teacher speed envelope. It is not a drop-in flight controller: the SAND.O function belongs to grid graph search, is Eigen/GraphSearch state-coupled, and this checkout has no call site for `computeNodeTime` beyond its declaration and definition. Its limits have not been matched to this x500/PX4 response. The function also does not certify obstacle clearance or window passage.

Policy-03 was the first completed policy result: it landed and disarmed after 77.000 simulated seconds, reached all 15 truth waypoints in order, passed all eight geometry checks, and cleared the modeled window envelope by 93.3 mm. The repository's boundary guard is a separate predictive planar heuristic configured with a 0.8 s velocity-response allowance, 0.4 s command lead, and 0.04 m position reserve; it neither copies SAND.O code nor inherits a formal safety proof. See the [policy results and limits](markerfree-policy-results.json), [recorded replay](media/window-policy.mp4), and [run comparison](flight-comparison.md). Policy-02 remains a useful unsuccessful trace for offline speed-envelope analysis. Do not adopt SAND.O's `v_max` or `a_max` as aircraft limits.

A subsequent [command-to-velocity trace diagnostic](experiments/braking-response-01/README.md) fits an effective first-order response to four completed Gazebo/PX4 runs. It provides a reproducible comparison with the guard's assumptions, but sampled closed-loop traces cannot establish a worst-case stopping bound. The flight guard parameters were kept unchanged.

## Command-delay scope

`computeNodeTime` uses an ideal per-axis acceleration/speed model with the supplied current velocity. It does not include command transport latency, controller update delay, or PX4 velocity-response lag. The checkout has `use_comm_delay_inflation` parameters, but at this commit `sando_node.cpp` only computes a timestamp age and stores it in `DynTraj::communication_delay`; repository search found no consumer of that stored field, `comm_delay_inflation_alpha`, `comm_delay_inflation_max`, or `comm_delay_filter_alpha` beyond declaration, parameter read, and logging. The active graph transition model therefore should be treated as latency-free. It cannot explain or compensate the observed policy-02 overshoot without adding a measured delay/response model.

## Why not build or integrate SAND.O now

The full project targets Ubuntu 22.04 / ROS 2 Humble and Gazebo Classic, and the package's top-level CMake requires Gurobi plus PCL and DecompROS2 components even when the desired target is small. Its planner core uses a Gurobi Hermite-spline optimizer; that is a substantial planner replacement with mismatched interfaces and dependencies for the current PX4 + Gazebo Harmonic + RGB-D stack. A full build, license setup, interface bridge, and aircraft calibration do not fit the remaining Mac disk/time budget. The project is a useful design reference, not an integrated planner in this repository.

The checked-out repo revision is `3efb0f812ddb96b65c421697a4e630376fabeed2`. `package.xml` declares BSD-3-Clause and the README says BSD 3-Clause, but that exact revision removed the repository `LICENSE` file. Treat the governing license terms as unresolved until the authors restore or confirm them; this note makes no reuse-rights claim.

## Evidence and dependencies

- The upstream [SAND.O repository at the checked-out commit](https://github.com/mit-acl/sando/tree/3efb0f812ddb96b65c421697a4e630376fabeed2) describes the global corridor planner and local Gurobi trajectory optimizer. Its [CMake file](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/CMakeLists.txt#L21-L58) requires ROS 2, Gazebo, Eigen, PCL, DecompROS2 packages, and Gurobi at configure time. The [README installation section](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/README.md#L75-L110) specifies Ubuntu 22.04 / ROS 2 Humble and a Gurobi WLS license for its Docker workflow.
- The [message-age calculation](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/src/sando/sando_node.cpp#L1137-L1148) only stores the age in a trajectory record; the [communication-delay fields](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/include/sando/sando_type.hpp#L99-L103) and [parameter declarations](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/src/sando/sando_node.cpp#L329-L333) are not evidence of active delay compensation in this revision.
- `package.xml` declares `BSD-3-Clause`; the [README license section](https://github.com/mit-acl/sando/blob/3efb0f812ddb96b65c421697a4e630376fabeed2/README.md#L401-L403) points to a LICENSE file that is absent in this commit. Verify terms with upstream before copying code.
- The [SAND.O paper](https://arxiv.org/abs/2604.07599) and [MIT project summary](https://computing.mit.edu/news/planning-system-ensures-a-robots-flight-path-will-remain-collision-free/) describe SAND.O as a planner for dynamic, initially unknown environments. That broader contribution is not equivalent to the scalar braking heuristic above and has not been validated on this simulator/airframe.
