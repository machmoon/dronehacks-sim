# Net-removed localization and OAK depth handoff

## Reuse the stereo odometry path for localization

The net-removed hover failure is evidence that the current Gazebo depth-map estimator can lose observability when its modeled net planes stop contributing stable depth constraints. The practical replacement for localization is already present in the Skybeta source tree: the OAK-D-S2 left/right image stream feeds NVIDIA Isaac ROS Visual SLAM (cuVSLAM), then `px4_odom_bridge` converts odometry to PX4 `VehicleOdometry`. cuVSLAM tracks image features across stereo views; it does not need the simulator's net mesh to be part of its map. It can therefore estimate motion from stable visual structure that exists in the real scene—such as textured walls, gate frames, and the floor—when enough features and stereo matches remain. NVIDIA describes cuVSLAM's image features, landmarks, odometry, and separate SLAM mapping thread in its [release 3.2 documentation](https://nvidia-isaac-ros.github.io/v/release-3.2/concepts/visual_slam/cuvslam/index.html).

The implemented path is specific and inspectable at Drone008 revision `31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8`:

- [config/oakd_vslam.yaml](https://github.com/AgastyaK87/Drone008_Dronehacks/blob/31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8/src/oakd_vslam_bringup/config/oakd_vslam.yaml) configures `/oak/left` and `/oak/right` raw images and camera info at 1024×640, 30 Hz, plus `/oak/imu/data`. It explicitly has no `stereo:` block and says the measured topic list contains no rectified or depth topic.
- [launch/oakd_vslam.launch.py](https://github.com/AgastyaK87/Drone008_Dronehacks/blob/31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8/src/oakd_vslam_bringup/launch/oakd_vslam.launch.py) converts each `bgr8` image to `mono8`, remaps the two images and camera-info streams into `VisualSlamNode`, and sets `rectified_images=False`. It supplies camera optical frame names and a static `base_link -> oak_parent_frame` transform. The defaults leave IMU fusion and mapping/localization mode disabled; the launch comments say pure stereo VO is the flight configuration and loop-closure pose jumps are avoided.
- [launch/px4_bridge.launch.py](https://github.com/AgastyaK87/Drone008_Dronehacks/blob/31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8/src/oakd_vslam_bringup/launch/px4_bridge.launch.py) and [oakd_vslam_bringup/px4_odom_bridge.py](https://github.com/AgastyaK87/Drone008_Dronehacks/blob/31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8/src/oakd_vslam_bringup/oakd_vslam_bringup/px4_odom_bridge.py) connect `/visual_slam/tracking/odometry` to `/fmu/in/vehicle_visual_odometry`, remap ENU to NED and FLU to FRD, forward the source sample timestamp, and increment the reset counter when `/visual_slam/status` reports loss followed by tracking reacquisition.
- The default pose-frame declaration is PX4 FRD because this stereo-only odometry starts at an arbitrary heading. The bridge's source comments explain that this frame is not north-aligned. Camera translation/rotation is passed as a static TF; the launch warns against also applying a nonzero PX4 EV lever arm.

This is the smallest principled way to stop using *modeled net planes as localization anchors*: feed stereo images into an odometer that estimates motion from their visual features and feed its odometry to EKF2. Keep the existing flight-interface boundary and PX4 state estimator. Do not use a net-removed route or hover result as a test of cuVSLAM; the two estimators consume different data and have different failure modes.

### What is evidence, and what is not

The ROS nodes, topic remaps, frame transforms, and launch parameters above are implemented in source. The repository's README and YAML comments report earlier rig measurements: clean 30 Hz at 1024×640, 118 MB/s driver traffic, and higher-resolution stereo-pair loss/sync problems. Those are recorded development-unit measurements, not new measurements made for this note. `Drone008_Dronehacks/docs/debugging.md` records one positive uXRCE-DDS connection with real payloads and also documents an unreliable TELEM2 connector; it is not proof of current fleet configuration. The source tree contains an EKF2 external-vision parameter file, but its own comments say it is not in the fleet flasher's default set and must be loaded only after checking the live odometry stream. A checked-in parameter file is not evidence of active EKF fusion.

The `official-drone-files` bundle contains the assembly CAD, camera-mount mesh, and coordinate/mount notes; it does not add a ROS launch, calibration, or stereo-depth configuration. The IMAV 2025 [Black Bee Drones README](https://github.com/Black-Bee-Drones/imav-2025/blob/master/README.md) is a useful independent architecture reference: it reports Isaac ROS Visual SLAM on a Jetson Orin Nano Super, with a hierarchical mission state machine and separate perception/control software. Its listed hardware is RealSense D435i plus a downward IMX219, and its flight stack is ArduPilot/MAVROS. It is not evidence that this Skybeta OAK/PX4 configuration works, nor a depth pipeline to copy.

The bridge copies the odometry header stamp to PX4 `timestamp_sample` and uses its ROS clock for PX4 `timestamp`. The host service code waits for system NTP synchronization and restarts the stack if the wall clock later steps, because such a step can make the camera's timestamps stale. This is a clock-handling measure, not proof of camera-to-PX4 absolute synchronization; acquisition-to-arrival delay, clock-domain agreement, and EKF delay still need live validation. The source code and local saved artifacts establish a packaged ROS design and limited development measurements/replays. They do not establish a cuVSLAM-on-OAK live flight in the net-removed scene or guarantee that natural scene texture is sufficient. Likely remaining VO failures include texture-poor walls/floors, motion blur, repeated gate patterns, lighting changes, camera vibration, stereo mismatch, and unmodeled camera-to-body extrinsics. Stereo VO without IMU fusion has arbitrary startup yaw and can drift; the local launch does not enable loop closure for flight. Validate tracking state, feature support, odometry age/rate, drift against an independent reference, and PX4 innovation/fusion state on a safe test setup before relying on it for control.

## Register real odometry before using the policy

The real bridge converts axis conventions; it does not register the arbitrary cuVSLAM origin and heading to the course. Its [position/orientation conversion](https://github.com/AgastyaK87/Drone008_Dronehacks/blob/31d58c767b6e72cbe58ea3e5690e9ac9ec2b59e8/src/oakd_vslam_bringup/oakd_vslam_bringup/px4_odom_bridge.py#L129-L169) contains no course translation or yaw transform. A known launch point establishes translation, but heading must also be measured against the course axes. Changing the PX4 frame label to NED does not supply that registration.

The current [policy state conversion](../learning/inference.py#L99-L108) expects position-derived goal delta, velocity and yaw to describe the same course-aligned frame. The existing [CourseFrame helper](../mission/frames.py#L6-L35) can express a planar origin/yaw alignment, but is not wired into this policy flight path and assumes aligned vertical axes. Measure camera/body extrinsics and establish gravity alignment before using it; the real launch defaults its camera-mount transform to zero and disables cuVSLAM IMU fusion. Capture-aligned PX4 roll/pitch does not by itself align VO positions and velocities.

The simulator [interpolates PX4 state to the depth capture timestamp](../mission/state_history.py#L48-L66), with a bounded bracket and no extrapolation. A real adapter must first establish the camera/ROS/PX4 clock relationship and latency, then provide the same capture-time pairing. Pairing depth with the latest available state is insufficient. The bridge's tracking-reset counter informs PX4 of reacquisition, but does not clear policy actions or re-register the course. A future real policy adapter must stop and discard pending actions on a VO reset, then revalidate origin, heading and timestamps before resuming. None of those real-flight integration steps were exercised by the Gazebo run.

## Keep actor depth as a separate integration task

The localization chain above does **not** provide an actor depth input. Current Skybeta YAML explicitly instantiates the stereo image path without a `StereoDepth` node, and its measured topic list has no depth. Luxonis documents `StereoDepth` as a separate depth/disparity producer with alignment, confidence, and left-right-check choices ([StereoDepth node](https://docs.luxonis.com/software-v3/depthai/depthai-components/nodes/stereo_depth), [ROS driver parameters](https://docs.luxonis.com/software-v3/depthai/ros/parameters)). That API is a candidate for a future measured depth publisher, not proof the pinned driver config already exposes one.

Before real OAK depth can reach the learned actor, an explicit adapter and offline evidence are still needed:

1. Enable and verify a pinned-version `StereoDepth` output and its ROS publisher; record the selected left/right sockets, rectification, alignment target, baseline/intrinsics, output encoding/units, confidence threshold/map stage, and timestamps. The current actor consumes depth and estimated state, not RGB. Verify the depth projection and camera-to-body transform used by its preprocessor.
2. Preserve invalid pixels as **unknown**. The pinned DepthAI v3.7.1 [`StereoDepth.hpp`](https://github.com/luxonis/depthai-core/blob/v3.7.1/include/depthai/pipeline/node/StereoDepth.hpp#L102-L107) documents RAW16 millimetres and zero invalid/undetermined depth. The simulator policy path currently has Gazebo-specific far/clear semantics, including treating positive infinity as far/clear; an OAK adapter must never turn zero, NaN, or confidence-rejected depth into positive infinity/free space. The repo's [OAK handoff](oak-depth-handoff.md) already notes there is no OAK-to-policy adapter.
3. Measure real stereo behavior on the target net and background. Invalid holes, edge mixed pixels, and finite returns behind/through thin net are different cases. A confidence mask may be available only at a specific pipeline stage and may not align with the final aligned depth image; do not apply it pixelwise until that correspondence is demonstrated.
4. Build a unit-checked adapter that produces 384×256 metric optical-Z input for the existing policy preprocessor. Its assumed virtual camera is centered with a 90° horizontal field of view; arbitrary OAK intrinsics cannot be corrected by resizing alone. Validate calibrated projection, alignment, invalid-pixel handling, synchronization and camera-shift assumptions. Replay through `learning.inference.policy_depth`, which forms the actor's 24×16 normalized ray-range input, and then through the actor offline. Report valid-depth coverage by region, changed rays around net strands and boundaries, and actor output changes. Validate state/action timing and closed-loop behavior separately.

Do not treat a depth publisher, a reported frame rate, or a successful synthetic-depth flight as proof that real OAK returns are suitable for actor decisions. PX4 EKF2's external-vision fusion is a distinct localization path; its delay and external-vision control settings must be calibrated and checked from the live vehicle, as described in the [PX4 v1.16 EKF2 guide](https://docs.px4.io/v1.16/en/advanced_config/tuning_the_ecl_ekf).
